# План реализации: копия данных

Поведение — в `docs/spec.md` (3.20, 5.14). Здесь — как это строится. Макет — `docs/design/project/backup/project/Копия данных.dc.html`: кадры 21a (вход), 21b (состав), 21c (прогресс и итог сохранения), 21d (паспорт копии), 21e (нехватка места, прогресс, перезапуск, неудачи), 21f (уведомление), секция `dev`.

## Что берём из макета и что меняем

| Из макета | Решение |
|---|---|
| Выключатели состава, первая строка «всегда»; два пресета — для сравнения | Берём выключатели |
| Полоса долей веса, выключенная доля сереет, минимум 4 dp | Берём; токены — `ViolinTheme.backupColors` (не цвета зон) |
| Намёк «с тех пор 9 новых записей» — словами в подписи, условие: копии > 30 дней и есть новое | Берём; считаем записи (сессии и дубли) новее даты копии |
| Ссылка в онбординге только на шаге 1 | Берём |
| Последняя фаза «Проверяем файл» — архив читается обратно | Берём: второй проход чтения из выбранного места; удваивает чтение, но копия, которую нельзя открыть, хуже медленной |
| «WorkManager foreground» | **Не берём** (зависимость): своя служба переднего плана типа `dataSync`, работу ведёт синглтон `BackupManager` со своей областью, служба только держит процесс и уведомление |
| Оценка «1 мин / ГБ + 2 с», «осталось» после 5 % или 10 с | Берём; коэффициент дальше меряется на устройстве |
| Второй диалог «Заменить данные?» с числами | Берём |
| «Сначала сохранить текущие данные» возвращает на восстановление с тем же файлом | Упрощаем: ведёт на экран копии; после неё человек сам снова открывает «Восстановить» (URI файла одноразовый грант держит, но возврат «с тем же файлом» через два экрана — лишняя связность) |
| Перезапуск одной сценой, дальше «Занятия» | Берём: `MainActivity` после восстановления открывает вкладку «Занятия» |
| «Начать с чистого приложения» | Берём |
| Диалоги — текстовые кнопки, деструктивная справа | Берём (обычный `AlertDialog`), общий `DeleteDialog` здесь не подходит: это не удаление записи |
| Уведомление: заголовок с процентом, фаза, системная полоса, ongoing, без звука | Берём; иконка — новый `ic_stat_backup.xml` (статус-бару нужен ресурс, не `ImageVector`) |

## Решения, которых нет ни в спеке, ни в макете

- **Формат** — `core/backup`, чистый Kotlin: `BackupManifest` (пары «ключ = значение», `java.util.Properties` — `org.json` в unit-тестах не работает, своей JSON-библиотеки в проекте нет), `BackupWriter` (`ZipOutputStream`: паспорт первым, отметка конца `complete.txt` последней; база и настройки — `DEFLATED`, медиа — `DEFLATED` уровня 0: `STORED` потребовал бы знать CRC заранее, то есть читать каждый файл дважды), `BackupReader` (`ZipInputStream`: паспорт, распаковка с защитой от путей наружу, проверка отметки конца; CRC проверяет сам поток). Тесты на JVM на временных файлах.
- **Части**: `BackupPart.DATA / SHEETS / AUDIO / VIDEO`; путь в архиве говорит, куда файл вернуть: `db/violin.db`, `settings/user_settings.preferences_pb`, `profile/…`, `repertoire/…`, `sessions/…`.
- **Снимок базы**: под `BEGIN IMMEDIATE` (писатели ждут) копируются `violin.db` и `violin.db-wal`; снимок открывается обычным `SQLiteDatabase`, сливается контрольной точкой в один файл. База — сотни килобайт, это доли секунды.
- **Подмена при старте**, а не в работающем процессе: Room открыт Hilt-синглтоном, закрыть его «на лету» нельзя. `RestoreSwap.applyIfPending(context)` зовётся в `Application.attachBaseContext` — до Hilt. Шаги идемпотентны, отметка `restore-ready` снимается последней: прерванная подмена доедет при следующем старте.
- **Путь без страховки**: проверка архива целиком → удаление медиа (`sessions/`, `repertoire/`) — это и есть место → распаковка → отметка → перезапуск. Если распаковка сорвалась, база ещё есть, но без файлов: экран честно говорит «прежних данных уже нет»; «Начать с чистого приложения» ставит отметку `wipe` — старт стирает всё.
- **Удаление записи посреди копии**: писатель терпит исчезнувший файл (пропускает), запрета на удаление в трёх view model-ях нет. В спеке поправлено.
- **Недописанный файл** удаляется `DocumentsContract.deleteDocument`.
- **«Отправить…»** — архив в `cache/share/backup/`, обычный `ACTION_SEND` (`application/zip`); чистится вместе с остальным `cache/share` через сутки.
- **Системная автокопия**: `backup_rules.xml` / `data_extraction_rules.xml` исключают `files/sessions`, `files/repertoire`, `files/waveforms`.
- **Занято ли приложение**: `TakePipeline.recordingRequested` и `VideoTakeImporter.state`.

## Риски

- Облачные поставщики документов (Google Диск) на гигабайтах медленны и могут оборвать поток — ошибка «место сохранения стало недоступно»; надёжный путь — локальная папка.
- Проверка записанного файла требует, чтобы поставщик отдал только что записанное на чтение; если не отдаёт — копия считается сохранённой без проверки (в журнал), а не проваленной.
- ZIP64 на потоке: проверяется тестом с записью > 4 ГБ разреженными данными только на JVM (на устройстве — слишком долго).
- Перезапуск процесса: на части прошивок активность после `exit` поднимается с задержкой — сцена «Открываем ваши данные…» может мигнуть чёрным; проверяется на телефоне.

## Как вышло

Все четыре этапа сделаны за один заход. Unit-тесты и lint зелёные, `AppBackupStoreTest` на эмуляторе зелёный.

- Проверено на эмуляторе (сборка `-PfakePitch=true`): блок «Данные» в «Настройках», экран состава с весами и полосой долей, «Сохранить в…» → системное окно → файл 1,5 МБ в «Загрузках» (на хосте открывается `unzip`, паспорт и `complete.txt` на месте), экран «Копия сохранена», подпись «последняя — 20 сентября»; «Восстановить из копии» → паспорт, «Сейчас в приложении», диалог «Заменить данные?» → перезапуск на «Занятиях»; то же в стёртое приложение через «У меня есть копия данных» — без второго подтверждения, онбординг не понадобился, 7 сессий и видео-дубль на месте.
- Отошли от плана: `POST_NOTIFICATIONS` пришлось объявить (lint-ошибка `NotificationPermission`, и без объявления уведомления не увидит никто); запрашивать его по-прежнему не запрашиваем. Обрезанный в хвосте архив потоковым чтением не считается повреждённым, если отметка конца прочитана, — центральный каталог нам не нужен. Путь без страховки отменяем только на фазе проверки.
- Поймано на эмуляторе: строка количеств первой части обрезалась в одну строку («… · 1 трофей» не было видно) — разрешены две.
- На эмуляторе у произведения три страницы в базе, а файлов фото нет (база подкладывалась руками) — поэтому «Фото нот» весит ноль; сами фото проходят круг в `AppBackupStoreTest`.
- Не проверено: гигабайтные копии и их скорость, облачные поставщики, уведомление и сворачивание посреди копии, отмена и удаление недописанного файла руками, путь без страховки и экран худшего случая руками, «Отправить…», намёк «с тех пор N новых записей» глазами, landscape, TalkBack, телефон.
