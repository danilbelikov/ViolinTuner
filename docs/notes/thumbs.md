# Заметки по коду · Кадр видео в списках

> Поведение — `docs/spec/thumbs.md` (3.38, 5.31). Читай перед работой над этой фичей; дополняй здесь же.

Этапы 131–132 (04.10.2026). Не проверено: на телефонах (Pixel владельца и iPhone) — ни плитка, ни переделка старых миниатюр на настоящих видео со штатива; какой кадр «середина» даёт на длинных GOP (видео из мессенджеров, монтаж) — берётся ближайший опорный, он может отстоять от середины на секунды; TalkBack и VoiceOver на карточке с кадром.

- **Файл миниатюры прежний** — `<имя видео без расширения>-thumb.jpg` в `sessions/`, имя на обеих платформах даёт `VideoThumbs.nameOf` (`shared/…/core/recording/video/VideoThumbs.kt`): `AppVideoFiles`, `IosVideoFiles`, `AppSessionAudioFiles`, `IosSessionAudioFiles` (удаление, чистка сирот, `thumbOf`). До 0.92 `AppVideoFiles` строил имя через `removeSuffix(".mp4")`, и у видео с iPhone (`.mov`, пришедшего копией данных) Android искал `<uuid>.mov-thumb.jpg` — миниатюры не было ни в листе разбора, ни на «Выступлениях». Новое имя файла (`-frame.jpg` и т. п.) не заводить: чистка сирот старых версий удалила бы неизвестный файл через сутки, а копия данных возит папку целиком.
- **Какой кадр** — `VideoThumbs.momentsMs` (середина, 0 с, 1 с; без длительности — 0 и 1 с, как до 0.92) и `VideoThumbs.pick` (первый не тёмный; тёмные все — первый найденный, то есть середина; каждый не взятый кадр — в `discard`: на iOS это `CGImageRelease`, на Android — `Bitmap.recycle`, кадр 1080p — 8 МБ). «Тёмный» считает платформа прежним правилом (`AppVideoFiles.isDark`, `IosPictures.isDark`). Кадр — ближайший опорный: `OPTION_CLOSEST_SYNC` на Android, допуски `AVAssetImageGenerator` по умолчанию на iOS — одно поведение на обеих.
- **Запись через `.part`.** Android пишет `…-thumb.jpg.part` и переименовывает (`renameTo` заменяет); iOS — `IosPictures.writeJpeg`, который теперь ставит файл на место `IosFolders.replace` (`rename(2)`), а не `moveItemAtPath`: тот отказывает, если имя занято, и переделанная миниатюра молча не вставала. `.part` копия данных не берёт (`listing` пропускает), чистка сирот уберёт забытый через сутки.
- **Путь к кадру** читает хранилище записей: `SessionMapper.toSummary(entity, thumbOf, soundFound)` спрашивает `thumbOf` только у видео, чей файл найден (`soundFound`), — `RoomSessionRepository` отдаёт `SessionAudioFiles.thumbOf(name)?.filePath`. У `SessionAudioFiles.thumbOf` умолчание `null`: пять тестовых фейков интерфейса не менялись. Порядок параметров `toSummary` — `thumbOf` перед `soundFound` намеренно: тесты зовут `toSummary(entity) { … }` с хвостовой лямбдой для `soundFound`. Дальше путь идёт сам: `SessionSummary.thumbPath` → `HistoryReducer.cardOf` → `HistoryCard.thumbPath` (все списки карточки — «Записи», лист дня, дубли, события, «Слушать на…»), `SoundViewModel.nameOf` → `RecordingName.thumbPath` (строка «Слушать на») и `PerformancesViewModel` → `PerformanceCard.thumbPath` (по имени видео из той же сводки; свой `VideoFiles.thumbOf` и память путей у «Выступлений» убраны, `VideoFiles` из их конструктора — тоже). Новых запросов к диску на экранах нет: на каждый выпуск списка — один `stat` на видео в том же проходе, где уже проверяется файл звука.
- **Кадры — только по текущему правилу.** `RoomSessionRepository` (параметр `thumbRules`) ищет миниатюры, только пока `VideoThumbRuleStore.rule` не ниже `VideoThumbs.RULE`: `sessions` — `combine(dao.observeAll(), thumbsReady)`, `details` и `summary` читают отметку один раз. До отметки `thumbPath` у всех `null` — в списках прежняя камера; встала отметка — список приходит заново с путями. Без этого (так было в первой версии этапа) симулятор с `-openRoute history` показал у переделанного видео старую миниатюру: карточка прочитала файл раньше прохода, а `rememberSmallFileImage` держит картинку по пути до конца процесса. `thumbsReady` объявлен до `sessions` намеренно: свойства инициализируются по порядку, и `sessions` собирается из него.
- **Плитка** — `RecordTile(…, thumbPath)` → `FrameTile`: квадрат 40 со скруглением 10, `surfaceContainerHigh`, камера под кадром, `Image` с `ContentScale.Crop` и `BiasAlignment(0, −0,5)`; кадр читает `rememberSmallFileImage` (память на 48 картинок, общая с нотами и фото профиля). Проявление 150 мс — `Animatable` от 0, только если кадра не было в памяти при первом показе; при «убрать анимации» (`LocalReduceMotion`) — сразу. Кадр рисуется, только когда `hasAudio && hasVideo && thumbPath != null`: потерянное видео — прежний контур, видео без миниатюры — прежний круг. Отметка выбора — прежний `Crossfade` в `RecordCard`, ширина та же.
- **Переделка старых миниатюр** — `Housekeeping.remakeThumbs` из `atStart` (параллельно с чисткой сирот): если `VideoThumbRuleStore.rule` < `VideoThumbs.RULE` (2), то по записям из `sessions.sessions.first()` (новые первыми), у которых найден звук и есть видео, — `videoFiles.existing(name)?.let(makeThumb)` по одной на `io`, затем `markRule(2)`. Отметка — `video_thumbs_rule` в файле настроек (`DataStoreVideoThumbRuleStore`; Android — `SettingsModule`, iOS — прямо в `IosGraph`, один экземпляр на хранилище записей и уборку). Пока проход идёт, кадров в списках нет (пункт выше): на телефоне с десятками видео первые секунды после обновления у видео — камеры.
- Тесты: `VideoThumbsTest` (`commonTest`: имя, моменты, выбор), `SessionMapperTest` (путь только при найденном файле), `HistoryReducerTest` (карточка несёт путь), `PerformancesViewModelTest` (путь из сводки), `RoomSessionRepositoryThumbsTest` (`commonTest`: до отметки путей нет, после — есть), `HousekeepingThumbsTest` (`app/src/test`: раз, новые первыми, неудача не останавливает, текущее правило — ничего), `AppVideoFilesTest` (`androidTest`: середина, тёмная середина → первый кадр, замена целиком без `.part`, `.mov` находит миниатюру), `IosVideoThumbTest` (`iosTest`: середина, тёмная середина, замена при занятом имени). `TestVideo.make` получил `luma` — яркость кадра по номеру; он стоит перед `hzAt` намеренно: тесты разбора передают `hzAt` хвостовой лямбдой, и параметр после него перехватил бы её.
